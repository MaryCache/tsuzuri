English: [README.en.md](README.en.md)

tsuzuri は Claude Code に日本語の文章を執筆させる際に、AI が生成した文章の品質を向上させるためのスキルと閲覧アプリです。
ユーザーは閲覧アプリで文ごとに AI の執筆意図（その文で読み手に何をするか）と文機能（文の役割や前の文との接続）を確認し、違和感を覚えた文にコメントを残して、AI に修正を依頼できます。

この README も tsuzuri で執筆しました。
この README では執筆意図を先に記述させる理由、使用方法、執筆の手順と文機能の語彙の根拠を、その順に説明していきます。

## 執筆意図を先に記述させる理由

私は、「まとめて文章を生成させると、どうにも AI の思考が自分の手から離れた感覚がして扱いづらい」と感じていました。
tsuzuri のアイデアの根幹は、その感覚を元にした「AI が何を考えてその文を書いたのかを可視化できれば、レビューが容易になるのではないか」というお風呂中の思いつきです。

tsuzuri は一文を執筆する前に、その文で読み手に何をするかを執筆意図として AI に先に記述させます。
執筆したあとには、その文の役割・前の文との接続・重要度を、文機能として AI に付与させます。

ユーザーは一文ごとの役割と、AI が何を考えてその文を執筆したかを読んで理解できます。
意図がずれている箇所や、言い回しが気に入らない箇所を発見した場合は、コメントすることで AI に修正を依頼できます。
執筆意図と文機能がその一文の果たすべき要件と持つべき性質を示しているため、ユーザーもその要件に見合う文を自分で提案しやすくなります。

## 要件定義から推敲までの執筆の流れ

「tsuzuri で書いて」と依頼すると、AI は次の順で文章を執筆します。

1. 要件定義書で、何を誰のためになぜ執筆するか、何を扱い何を扱わないか、読み終えた読み手が何をできるようになるかを決定します。
2. 設計書で、段落ごとの主張と順序を決定します。
3. 一文ずつ、執筆意図、文、文機能の順に執筆します。
4. 執筆を終えた文章を、各文が執筆意図を果たしているかでレビューし、改善の案を AI 自身が反映します。
5. 校正辞書（標準の辞書と、ユーザーが追加した辞書）に沿って表記を統一し、yomiyasu（日本語の言い回しを推敲する別のスキル）で言い回しを推敲します。
6. 設計書や執筆意図を与えない別の AI に読ませ、何を指すか理解できずにつまずいた箇所を修正します。

手順4で、材料に無い事実が必要な案と、意味・数値・確かさ・強さが変わる案は反映せず、AI がその理由をユーザーに伝えます。
依頼の際に「要件で止めて」「設計で止めて」と指定すると、AI はその段階で停止し、ユーザーは要件定義書や設計書にコメントを付けることができます。

## 閲覧アプリでの確認と修正の依頼

完成した文章を閲覧アプリで開いて文を選択すると、その文の執筆意図と文機能が右の詳細パネルに表示されます。
違和感を覚えた文にはコメントを残し、「tsuzuri のコメントを読んで直して」と依頼します。
AI はその文を修正し、新しいバージョンに更新します。

新しいバージョンには何を直したかを1行で表すタイトルが付き、文を選択したときのバージョン履歴に表示されます。
修正前の文も記録（「記録の保存先と git」の節）に保存され、アプリはそれと新しい文との差分を表示するため、修正箇所を確認できます。

画面の読み方はアプリを初めて開いたときに表示されるクイックスタートガイドで説明しています。

## 人や AI が執筆した文章を読む

人やほかの AI が執筆した文章も、「tsuzuri で読んで」と依頼すると、AI が一文ずつ文機能を付与します。
人の文には書き手の執筆意図が無いため、AI は文と前後から推測した執筆意図を付与し、アプリはそれを推測であると明示して表示します。

自分や人が執筆した文章を読ませると、AI はレビューも行って弱い文を指摘するため、そのまま修正も依頼できます。
このとき AI は改善の案を自動では反映せず、ユーザー自身の原稿のようにユーザーが直す前提の文章なら、反映してよいかを確認します。

AI が生成した冗長な公開記事も、サイドバーの重要度の見出しの右でフィルターを選んで「核」（消すと言いたいことが失われる文）を押せば、核の文だけが残るため、本筋を追って読むことができます。

ほかのチャット AI が執筆した文章なら、アプリのライブラリ（文章・テンプレート・校正辞書・プロンプトを切り替えて見る画面。0 キー）で「プロンプト」に切り替え、書いた経緯を書き出させるプロンプトをコピーして、その文章を執筆させた会話に貼り付けて送信してください。
返ってきた答えを文章と一緒に Claude Code に渡すと、AI は推測ではなく、執筆した AI 自身の説明から執筆意図を記録します。

## テンプレートと校正辞書

テンプレートと校正辞書は、ユーザーの決まりと好みを tsuzuri に残しておく場所で、足すほど初回生成の文章がユーザーの好みに近づきます（考え方は「設計の考え方」の「読解の補佐と、好みの言語化」）。

テンプレートは文章の種類ごとに、用途・分量や文体の既定・見出しの構成を定めたものです。
README・仕事の報告と提案・ブログとエッセイの3つを標準で用意しています。
依頼の際に「README のテンプレートで」のように名前を指定すれば、AI はそのテンプレートを使用します。
名前を指定しなければ、AI は依頼内容に最も近いテンプレートを選択し、該当するものが無ければテンプレートを使用せずに執筆します。

社内の記事のように見出しの構成が決まっている文章は、`~/.config/tsuzuri/templates/` に自分のテンプレートを追加して使用できます。
ファイル名がそのままテンプレートの名前になり、依頼の際にその名前で指定できます。
内容は標準のテンプレート（`skills/tsuzuri/references/templates/`）を複製して編集すると作成できます。
参考にしたい文章を渡して「この文章をもとにテンプレートを作って」と依頼すれば、AI が用途・文体・見出しの構成を読み取ってテンプレートを作成します。
標準のテンプレートと同じ名前にすると、標準のものに代わって自分のテンプレートが使用されます。

「要件定義から推敲までの執筆の流れ」の手順5で使用する校正辞書には、好みの語や文章固有の呼称を追加できます。
`~/.config/tsuzuri/words.tsv` に「探す形・直す先・補足」を1行ずつタブ区切りで記入すると、標準の辞書と併せて使用されます。
コメントで語の言い換えを求めると、ほかの文章にも同じ直しが要りそうなものは AI が自動で辞書に1行追加し、追加したことを伝えます。

文機能の接続（前の文とのつながり）と役割（文の働き）に既定以外の語を使用する場合は、その文章の記録フォルダ（「記録の保存先と git」の節）の `vocab.json` に追加できます。
テンプレートと校正辞書の一覧と内容は、アプリのライブラリの画面で表示を切り替えて確認できます。

## 導入方法

使用するには、Claude Code、Python 3.10 以上、yomiyasu と、導入時に使用する Node.js（npx）と git が必要です。
yomiyasu は日本語の言い回しを推敲するスキルで、tsuzuri は執筆を終えた文章をこれに通します。
スキルは次のコマンドで導入します。

```bash
npx skills add MaryCache/tsuzuri
npx skills add nanaism/yomiyasu
```

閲覧アプリはスキルに含まれないため、リポジトリを手元に複製します。

```bash
git clone https://github.com/MaryCache/tsuzuri.git
```

現時点では、対象は日本語の文章のみです。

## 閲覧アプリの起動

閲覧アプリは次のコマンドで起動し、表示されたアドレスをブラウザで開きます。

```bash
python3 tsuzuri/app/server.py
```

クイックスタートガイドも tsuzuri で執筆した文章であるため、読みながら文を選択し、執筆意図と文機能を確認できます。
ライブラリに無い記録フォルダ（「記録の保存先と git」の節）は `python3 tsuzuri/app/server.py <ファイル名>.tsuzuri` のように指定して開くことができ、ポートは `--port` で変更できます（既定は 8770）。

## 自分の文章での試用

自分の文章で試用する際は、何を誰に向けて執筆したいかを明示して、Claude Code に「tsuzuri で書いて」と依頼します。
tsuzuri で執筆した文章はアプリのライブラリ（0 キー）から開くことができます。

## 記録の保存先と git

要件定義書・設計書・各文の執筆意図と文機能・コメントは、文章のファイルの隣の「ファイル名.tsuzuri」というフォルダに記録として保存されます。
tsuzuri は文章のファイルを置いたリポジトリの `.gitignore` に `*.tsuzuri/` を追加し、記録フォルダを既定で git の対象外にします。

記録を git に含めて公開すると、執筆意図とコメントも公開されます。
git の対象外のまま記録フォルダを削除すると、git では復元できません。
執筆意図とコメントを公開せずに残したい場合は、記録フォルダを別に保存してください。

## 記録の共有

記録を人と共有したい場合は、Claude Code に「この文章の記録を共有ファイルにまとめて」と依頼すると、記録と文章が1つの共有ファイル（`.tsz`）にまとまります。
受け取った人はアプリのライブラリの見出しの右にある「共有ファイルを開く」で `.tsz` を選択するか、ライブラリへファイルをドラッグすると、その文章を開くことができます。

共有ファイルにも執筆意図とコメントが含まれるため、渡す前に公開してよい内容かを確認してください。

## 設計の考え方

### 読解の補佐と、好みの言語化

最初の時点では、tsuzuri は文章をユーザーの好みどおりに自動で仕上げるツールではありません。
あくまで、人間がレビューしやすい環境を整え、読解を補佐するツールです。

tsuzuri がユーザーに渡すのは、日本語として正しいとされる読みやすく癖の少ない文章と、その一文一文を執筆したときの思考の経緯（執筆意図）の2つです。
そこから自分の好きな文章に仕上げるのはユーザーの仕事で、些細な言い回しの好みにまで AI がすべて先回りして合わせることは目指していません。
その代わり、文と思考の経緯を比較しながら読めるため、ユーザーが思い描く「ぼくのかんがえたさいこうのぶんしょう」と食い違う箇所を、文を指して言語化するハードルを限りなく下げることができます。

AI は次に執筆する前に、コメントで直した文の修正前と修正後をお手本として読みます。
さらに、言い換えを求めたコメントは AI が校正辞書に追加し、決まった構成はユーザーがテンプレートに追加しておけるため（「テンプレートと校正辞書」の節）、使い込むほど初回生成の品質が高くなっていきます。

### 要件定義書と設計書を先に決定する理由

目的を定めてから構成を作成する順序は、技術文書の教材（Google Technical Writing）にも、日本語の作文指導（金子 2003）にもあります。
執筆する前に構成を決定すると、紙に書かず頭の中で組み立てただけでも、紙に書いたときと同じだけ文章の質が向上したという実験があります（Kellogg 1988）。

一方で、構想の指導の効果は項目によって分かれ、主題の質には効果が見られなかったという報告もあります（高橋）。
そのため tsuzuri は主題の質を、要件定義書の各項目に「読み手は何を得るか」と問うことで確認します。

### 執筆意図に問うこと

tsuzuri は、各文の執筆意図を果たしたとき読み手が何を得るか、つまり読み手の「だから何？」に答えているかを問います。
語りの研究では、聞き手の「だから何？」に答える部分を evaluation（評価）という用語で呼び、話が語るに値することを示す部分としています（Labov）。

答えられない執筆意図は、書き手が考えた順序をそのまま映していることがあります（Flower 1979 は、読み手でなく書き手の都合で並んだ文章を Writer-Based prose と呼びました）。
そのため tsuzuri は、答えられない執筆意図を、読み手が得るものから記述し直させます。

### 文機能の語彙

接続は市川孝（1978）の文の連接8類型、役割は木戸光子（1992）の新聞投書の6分類を採用しています。
重要度は、消すと言いたいことが失われる核（nucleus）と、それを支える衛星（satellite）の2つで、修辞構造理論（RST）の注釈手引き（Carlson & Marcu 2001）から採用しています。

文の接続や重要度は、人どうしでも判定が一致しにくいと報告されています（Prasad ら 2017、Zeldes ら 2026）。
そのため文機能は正解として扱わず、読んで異なると判断した場合はコメントで修正してよい目安として付与しています。

### 読み手の負担を確認する理由

教科書の章を要点だけの要約にして読ませると、全文を読んだ人より要点の記憶も推論の問いも優れ、その差は6〜12か月後まで持続しました（Reder & Anderson 1980）。
つまり、衛星にあたる細部を追加するほど理解が深まるとは限りません。

内容が一つの文は、内容が複数ある文より、内容を問う質問への解答時間が短かったという実験もあります（吉田・中山 2002）。
文や細部をどこまで削減すべきかを数値で定めた研究は見つからなかったため、tsuzuri は長い文や衛星の多い段落を、見直す候補として提示するにとどめています。

### 文脈の無い読み手に読ませる理由

書き手は自分の文章の意図を知りすぎているため、読み手がつまずく所に自分では気づきにくくなります（Caltech Hixon Writing Center）。
読み手の反応の記録を用いて指導を受けた書き手は、読み手の視点に立つ力が有意に向上したと報告されています（Schriver 1994）。
そのため tsuzuri は、執筆の文脈を持たない別の AI につまずいた箇所を報告させ、その反応をもとに修正します。

ここで挙げなかったものも含め、出典の書誌はスキルの `skills/tsuzuri/references/` の各ファイルにあります。
